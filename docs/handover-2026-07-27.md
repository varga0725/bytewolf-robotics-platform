## What was built recently, and what it is worth

### Phase C — the Offboard control boundary

`brain/control/` — the only path by which a streamed setpoint could reach PX4.
Contract, stateful boundary, watchdog, session. `brain/adapters/offboard_velocity_adapter.py`
carries approved velocities to MAVSDK and nothing else.

**Disabled by default**, twice over: `safety.offboard.enabled` is false in
`twin.yaml`, and a session runs in shadow mode unless an explicit argument says
otherwise. Neither switch alone goes live.

The SITL run found something unit tests could not: **MAVSDK re-sends the last
setpoint at 20 Hz**, so a producer going quiet does not make the link go quiet.
The vehicle keeps flying a command this platform has already declared void.
That is why the fallback is *executed* (`brain/adapters/offboard_fallback.py`)
rather than merely decided.

### Phase D1 — the runtime safety shield

`brain/control/shield.py`. Geometry only: distances, sector coverage, a
conservative stopping estimate. **Deliberately not a CBF** — a CBF constrains a
dynamics model and this twin has none measured (every physical parameter in
`twin.yaml` is still `provenance: simulated`, from PX4's generic x500). A CBF
built on those numbers would be a precise statement about a simulator.

G4 evidence, `simulation/artifacts/control/shield-repeatability-20260726T161358Z.json`:

```
shield.v1 (active) — 40 runs
  clear-path        9/10   (threshold 0.9)
  static-obstacle  10/10   worst clearance 3.07 m against a 2.00 m standoff
  blind-sector     10/10
  stale-sensor     10/10
```

The shield's value is visible in the difference between modes: in shadow the
vehicle flew on to 1.65 m; in active it stopped at 3.14 m. Same judgement, and
only one of the two runs had anyone act on it.

**The clear-path anomaly is open and unexplained.** One run in ten intervened
30 times in an empty world, first sensing something 2.003 m dead ahead. It has
appeared three times and been reproduced never. It sits under the configured
threshold; it is not understood. The instrumentation records *where* but not
*why*, because no sample carries the vehicle's altitude or attitude — that is
the next diagnostic step if it matters to you.

### The shield does not protect the mission path

This is the most important architectural caveat. The shield guards the
**Offboard setpoint stream**. The chat/MissionSpec path flies `goto_location`
(Auto/Hold), which the G3 measurement showed nothing protects — PX4's Collision
Prevention runs only in Position mode and let the vehicle reach 0.36 m from an
obstacle. Moving the shield onto the mission path is a separate, unstarted
piece of work.

## The live simulation stack

All of it runs from the repo root with the project venv.

```bash
# 1. Simulator with a visible window. PX4 stays in daemon mode; the GUI is a
#    second process because macOS gz sim cannot be server and GUI at once.
BYTEWOLF_GZ_GUI=1 ./simulation/gazebo/launch/run_px4_gazebo_headless.zsh hawkeye-front

# 2. Telemetry bridge (needed for the dashboard and to satisfy PX4's GCS check)
.venv/bin/python -m brain.cli.dashboard_telemetry

# 3. API + Control Room + public site
.venv/bin/python -m apps.api.server        # http://127.0.0.1:8080/control-room/

# 4. A flight
.venv/bin/python -m brain.cli.fly_takeoff_hover_land
```

### Profiles

| Profile | Carries |
| --- | --- |
| `base` | nothing; cheapest, use when diagnosing |
| `hawkeye-front` | front camera only, at the twin's declared Hawkeye geometry |
| `full-sensors` | front camera + down camera + 2D lidar |
| `lidar-2d`, `mono-down`, … | PX4 stock airframes |

`hawkeye-front` renders `horizontal_fov 2.793` (160°) and 3840×2160, as
`twin.yaml` declares for the real Hawkeye 4K Split V5. Until today nothing
applied the FOV — the overlay carried PX4's stock 1.74 rad however the twin was
written, so the contract described a lens the simulation never rendered.

**4K starves the sensor bridge on this machine.** Streaming it produced BARO,
MAG and gyro timeouts. `BYTEWOLF_CAMERA_PIXELS=1920x1080` trades rendered
resolution for simulation rate without touching the FOV; at 1080p the timeouts
stop entirely.

### What this machine can carry at once

The Gazebo GUI alone costs ~130% CPU. Beside it, roughly one more consumer
fits. Loading it with the GUI, two camera streams, a survey recorder and a
1600×1600 map render every 20 seconds pushed the load past 9 and PX4's
accelerometer timed out — from which PX4 does not recover; the stack has to be
restarted.

`simulation.gazebo.map_view` must **not** run on an interval: the basemap is
static terrain and does not change. Render it once with `--once`. CLAUDE.md
also forbids it during evidence runs, because it injects a camera into the
world.

## Bugs found and fixed today, and what each cost

Recorded because the failure modes are more instructive than the fixes.

1. **The drone spawned nose-down.** From `z=2` it fell onto sloping Baylands
   ground and settled at pitch −60.6°. PX4 refuses to arm and reports only
   `Preflight Fail: Attitude failure (pitch)`, which reads like an estimator
   problem. Hours went into thermal throttling, simulation rate and camera load
   before one line of Gazebo ground truth showed the vehicle lying on its face.
   Both launchers now spawn at `z=0.4`; a test pins both, because they had
   already drifted apart.

2. **Both camera streams wrote the same files.** `--sensor down` defaulted to
   the front camera's `camera.jpg` and `detections.json`, so running the two
   together had them overwrite each other several times a second. On screen
   that was a flickering image alternating between the views. Nothing failed
   anywhere; a human watching found it.

3. **The mission map scaled to `max_radius_m`.** The envelope's widening to
   2 km made one screen pixel worth ten metres, the aerial basemap 18 px and a
   2 m obstacle cell a fifth of a pixel. Now a fixed 50/200/500 m choice.

4. **The shield failed open.** It recognised `unobserved` and `measured` and
   let every other coverage value through as clear — in the one component whose
   whole premise is that it fails closed. The observation schema happens to
   reject those today, which is why the 40-run matrix could not have caught it,
   and why the matrix evidence still stands.

5. **`test_camera_stream.py` declared a class twice**, so four tests had
   stopped running silently — including the one covering full-sensor topic
   selection.

## Known open items

- **The down camera sees its own landing legs**, roughly a third of frame.
  Affects detection. Unfixed. The overlay is ours (`simulation/gazebo/camera_profiles.py`),
  so the pose or FOV can be changed freely.
- **Object detection finds nothing in Baylands.** This is correct behaviour:
  the default backend looks for a red marker and the world is grass and trees.
  For visible detections, either spawn a marker or wire a real YOLO backend.
- **The clear-path shield anomaly** described above.
- **CI is red** and has been for a long time. Not billing — another workflow on
  the same repo runs fine. The `tests` workflow fails at 0 executed steps. The
  workflow also installs only `requirements.txt`, so the vision tests would
  skip even if the runner worked.
- **The survey recorder needs an explicit home** when PX4 reports `in_air`
  while the vehicle sits at 0.2 m: pass `--home-latitude/--home-longitude`.

## Ground rules worth keeping

- `twin.yaml` is the single source of every limit. A second copy of a limit is
  a design regression.
- Evidence carries its proof level. `unit/contract` is not `app+SITL`, and
  neither is a flight claim.
- A scenario that cannot fail proves nothing. Three separate scoring bugs were
  found this way: a run that scored its own land command as PX4 reacting, a run
  that passed on 109 straight sensor failures, and a run that blamed the shield
  for an obstacle it was never shown.
